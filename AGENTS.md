# AI Assistants & Developer Protocol

Welcome to the repository. This project is built collaboratively by developers and AI agents for a hackathon.

To ensure continuous alignment, eliminate context loss across sessions and developers, and maintain a single source of truth, all contributors (human and AI) must follow the directives below.

---

## 🧠 Core Directives for AI Assistants

### 1. Mandatory Context Loading
Before writing any code, planning changes, or executing commands:
- Inspect `.agents/skills/` (starting with [flowpay-core](file:///.agents/skills/flowpay-core/SKILL.md)).
- Read and adhere to the 3 foundational questions:
  1. **What is the app about?** (Vision, core problem, user personas, architecture).
  2. **What has been done?** (Existing modules, components, APIs, schema, tests).
  3. **What needs to be done?** (Prioritized roadmap, pending tasks, immediate next steps).

### 2. Mandatory Skill Updates on Every Build
Whenever you create, refactor, or complete any feature, component, API, or system:
- **Update the Master Skill ([flowpay-core](file:///.agents/skills/flowpay-core/SKILL.md))**:
  - Keep **"What Has Been Done"** strictly up-to-date with completed deliverables.
  - Update **"What Needs To Be Done"** by checking off completed items and refining the backlog.
  - Update any architectural or stack adjustments.
- **Create Subsystem Skills for Substantial Modules**:
  - Whenever a major subsystem is introduced (e.g., frontend, smart contracts, backend/indexer, payment engine), create `.agents/skills/<module-name>/SKILL.md` using the template at [MODULE_SKILL_TEMPLATE.md](file:///.agents/skills/templates/MODULE_SKILL_TEMPLATE.md).

### 3. Official Stellar Documentation & Secrets Protocol
- **Single Source of Truth**: FlowPay runs on the **Stellar network** (testnet). Consult the official docs at [developers.stellar.org](https://developers.stellar.org/) (LLM index: [developers.stellar.org/llms.txt](https://developers.stellar.org/llms.txt)) and the SEP specs at [github.com/stellar/stellar-protocol](https://github.com/stellar/stellar-protocol/tree/master/ecosystem) before implementing any Stellar feature. Read [.agents/skills/stellar/SKILL.md](file:///.agents/skills/stellar/SKILL.md) first.
- **Secrets**: Never hardcode secret keys (`S...`), API keys or webhook secrets. Server-side testnet keypairs are generated by `backend/scripts/stellar-bootstrap.ts` into the gitignored `.env`. User secret keys exist only on the user's device. Whenever an implementation needs a third-party credential (anchor, Paystack, SMTP, Gemini), ask the user for it.

## Rule: never fabricate a success response on a failed Stellar call

This codebase moves money on the Stellar network (accounts, trustlines, payments,
path payments, payroll batches, anchor deposits/withdrawals) through
`backend/src/stellar/` on the backend and `mobile/lib/core/stellar/` on-device in
the Flutter app. Even on testnet, treat this as real money and real identity.

**When a call to Horizon or an anchor fails (throws, times out, returns a
non-success result), the failure must propagate as a failure.** Concretely:

- Never catch a Stellar error and return a synthesized transaction hash, account
  ID (`G...`), or signature in its place.
- Never catch a Stellar error and return `status: 'SUCCESS'` / `'COMPLETED'` /
  `success: true`. Only a Horizon response with `successful: true` and a real
  `hash` may produce a completed record.
- A submit **timeout is ambiguous**, not a failure and not a success: record
  `PENDING` and reconcile by transaction hash against Horizon.
- Never let a caught Stellar error result in creating or updating a database
  record that implies the operation succeeded (e.g. an employee with a made-up
  `stellarAccountId`, a payroll item marked paid with no on-chain hash).
- It's fine to log a warning and it's fine to have a fallback — but the fallback
  must be an honest one: a `FAILED` status with a real error message (include
  Horizon `result_codes`), a rethrown typed exception, or a documented
  degraded-read (serving a cached balance on a read failure is OK; inventing a
  transaction on a write failure is not).

**This does not apply to `DemoProvider` / `Demo*Repository` classes.** Demo
mode is an intentional, clearly-labeled simulation path selected via
`ProviderMode.demo` in `AppState`. The rule above is about the **live Stellar**
code path silently behaving like demo mode without saying so.

### Self-check before finishing any task that touches a Stellar call site

Before marking a task complete, check every `try { ... horizon / submit / anchor ... } catch`
block you touched or added, and confirm:

1. Does the `catch` block return anything that looks like a successful result
   (a hash, an account ID, a `SUCCESS`/`COMPLETED` status, `success: true`)? If
   yes, stop and fix it. This exact pattern caused a prior incident in this
   codebase (payroll, transfers, cards and employee creation all had it under
   BMONI; see `docs/prompts/fix-silent-bmoni-fallbacks-prompt.md`).
2. Does the caller (mobile UI, another service) have a way to distinguish
   "this succeeded" from "this failed and here's why"?
3. If you're tempted to write `// offline/sandbox fallback` inside a live-mode
   code path, stop — either gate it behind `ProviderMode.demo` or fail loudly.

## Other standing conventions
 
- New provider-facing features should extend the existing
  `DemoProvider`/`StellarProvider` (`AppState` in
  `mobile/lib/core/state/app_state.dart`) and `*Repository` interface pattern
  in `mobile/lib/core/repositories/` — don't introduce a new
  parallel abstraction for switching providers.
- Signing goes through `mobile/lib/core/wallet/wallet_signer.dart`
  (`walletSignerProvider`) — don't touch the Stellar keypair vault
  (`mobile/lib/core/stellar/`) directly from UI/provider code for signing operations.
