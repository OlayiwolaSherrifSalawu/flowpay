1. Product Specification
One-sentence pitch
A payroll platform that lets a company pay remote workers across multiple countries — in their local currency,
with instant spending cards — through one dashboard and one click, without ever touching foreign banking or
KYC paperwork.
Why this idea

Every step maps to a documented BMONI endpoint — no improvisation, no undocumented risk.

Judges have likely already seen several cross-border remittance apps built from the same docs; payroll for
distributed teams is a less obvious synthesis of two separate BMONI capabilities (the partner/employee
invite model + card issuance/limits).

It is visually demonstrable at every step (invite → fund → card → purchase), not just "a number changed."

The 10x hook below directly proves BMONI's core differentiator: multiple countries' banking infrastructure
hidden behind one simple action.
The 10x hook: "One Employer, Many Countries, One Bill"
The employer adds employees in two different countries (Nigeria + Mexico). They see one aggregate USD
total, click one button, and BMONI fans the payment out across two different currencies, banking rails, and card
systems — invisibly. This is the clearest possible way to show, not just claim, why BMONI's multi-rail
infrastructure is valuable.
2. Personas & Test Data

3. System Architecture
Actors

Employer (partner) — uses a web/mobile dashboard to invite employees, fund wallets, issue cards, and run
aggregate payroll.

--- PAGE 3 ---

Employee — receives an invite link, completes onboarding/KYC (pre-run for demo), and views their wallet +
card + local-currency payslip.

Your backend — a thin server that holds your partner API key, calls BMONI's REST API, stores your own
payroll-run metadata (BMONI has no native "payroll run" concept — this is your own abstraction layer on
top), and receives BMONI webhooks.
Data flow (high level)
 Employer App  --calls-->  Your Backend  --x-api-key-->  BMONI API
                                         <--webhooks----  BMONI API
Employee App  --calls-->  Your Backend  --x-api-key-->  BMONI API
                                         <--SDK signing--  On-device wallet (Flutter/RN)
Private keys are generated and stored on the employee's device (Android Keystore / iOS Secure Enclave) via
the BMONI mobile SDK. Your backend never holds a private key — it only relays signature requests to the
device and signed payloads back to BMONI.
4. Exact API Call Sequence
4.1 Invite & link an employee
 POST /v1/partners/employees/invite
  body: { email, country }
  -> employee receives invite link, completes KYC/onboarding on their own
webhook: employee.linked   (fires when employee is verified + wallet exists)
4.2 Fund the employee's wallet
 POST /v1/users/{userId}/smart-wallets/{walletId}/proposals
  body: { toUserId, sourceSmartWalletId, token, fromAmount }
  -> returns { proposalId, signPayload }
[sign signPayload on-device via SDK]
POST /v1/users/{userId}/smart-wallets/proposals/{proposalId}/sign
  body: { signature }
4.3 Issue a virtual card (do NOT use physical cards for the demo)
 POST /v1/users/{userId}/cards
  body: { cardName, cardColor, currency, type: "virtual", smartWalletId, nin }
  -> returns { proposalId, feeAmount, signPayload }
[sign on-device]
POST /v1/users/{userId}/smart-wallets/proposals/{proposalId}/sign
  body: { signature }
4.4 Show spending / audit trail
 GET /v1/users/{userId}/cards/{cardId}/transactions
  query: status, from, to, size
4.5 Nigeria-specific onboarding (Employee 1)
 POST /v1/users/{userId}/onboarding/start-nigeria

4.6 Mexico-specific onboarding (Employee 2, for the multi-country hook)
 POST /v1/users/{userId}/latam/mx/kyc/activate
  body: { smartWalletId }
4.7 The aggregate payroll click (your own orchestration, not a single BMONI endpoint)
BMONI has no native "pay N employees across N countries" endpoint. Build this yourself: your backend loops
over the funding + notification steps (4.2) for every linked employee in a payroll run, in parallel, and reports back
one aggregate success/failure summary to the employer UI.

Phase 0 — Setup (30–60 min)

Obtain sandbox API key.

Request test token funding from BMONI team (manual, do this first — it has lead time).

Confirm second demo country: Mexico is the best-documented second rail (CLABE deposit/payout fully


Sketch the 5 core screens (section 6) before writing code.
Phase 1 — Core single-country loop (Checkpoint: minimum demoable product)

Employer dashboard: invite one employee (Nigeria).

Employee onboarding using a pre-verified test persona — run this once ahead of time, never live.

Employer funds the employee's wallet.

Issue employee a virtual card.

Show a transaction on the card via the transactions endpoint.
Stop here and confirm this works end-to-end before building anything else. This alone is a demoable
product if time runs out.
Phase 2 — The 10x hook (Checkpoint: the differentiating moment)

Add a second employee, in Mexico.

Build the aggregate payroll summary screen: employer sees one USD total across both countries before
clicking run.

Click "Run Payroll" once → fans out into an NGN payout for employee 1 and an MXN payout for employee 2,
in parallel, behind the scenes.

Show both employees' results side by side in their own local currency after the single click.


Per-employee spend-limit presets (Contractor / Junior / Senior dropdown, using the set-limit endpoint).

Employee self-serve card freeze toggle (card status endpoint).

Simple audit log screen — just displaying transaction data you already have.
Phase 4 — Explicit cut list (do not attempt unless everything above is done early)

8. Stage-Day Risk Checklist

Pre-run KYC/invite for both demo employees before your slot — never do it live.

Use only virtual cards — no OTP dependency.

Have a screen-recorded backup of the full flow in case the sandbox is slow or down during your demo.

Confirm sandbox test tokens are funded ahead of time (manual request process — do not leave this to the
morning of).

Treat any 404 from BMONI as possibly "not ready yet" rather than "missing" — poll or retry before treating it
as an error, per BMONI's own documented error semantics.

9. Instructions for the Coding Agent
If you are an LLM agent building this project from this spec, follow these constraints:

Build strictly in the phase order defined in Section 5. Do not begin Phase 2 work until Phase 1's full loop
(invite → fund → card → transaction) is verified working against the BMONI sandbox.

All amounts sent to BMONI endpoints must respect the units documented per-endpoint: some use minor
units (e.g. cents, as strings), others use human-readable decimal strings — do not assume consistency
across endpoints; check the specific endpoint's documented format before sending a request.

Every BMONI request must include the x-api-key header. Store it as an environment variable, never
hard-code it or expose it to client-side code.

Any BMONI action that returns a signPayload or signatureRequest requires an on-device signature via the
mobile SDK before the flow can complete — do not attempt to fabricate or bypass this step.

Treat webhook payload verification (HMAC-SHA256 over the raw request body) as mandatory for any
webhook handler you write, even in the sandbox.

Do not build a real recurring-payroll scheduler; simulate it with a manually-triggered batch action per Phase
4's cut list.

Prefer completing Phase 1 and Phase 2 fully over partially completing Phase 3 polish items — the polish
items are additive and independently droppable.
