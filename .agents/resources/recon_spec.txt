BMONI Embedded Platform Reconnaissance
Executive Summary
BMONI is a modern non-bank fintech platform offering multi-currency digital wallets and global card
services via regulated stablecoins【59†L185-L194】【14†L81-L90】. It targets globally-connected users
(expats, freelancers, SMEs, parents abroad, etc.) who need to hold and move money across USD, NGN, EUR,
MXN, CAD, etc. BMONI partners with banks and regulated stablecoin issuers (Paxos, Monerium, Anchor ,
etc.) to back each stablecoin fully with fiat reserves【59†L272-L279】【14†L81-L90】. Users sign up via
mobile app (face-recognition KYC【59†L219-L224】), provision a self-custodied smart-wallet on device
(secure enclave/Ethereum keypair【32†L67-L75】), then perform on- and off-ramps across regions: e.g.
fund in NGN/NGN (→CNGN), USD/USD (→USDB), EUR/EUR (→EURe) and offload via local bank payouts or
crypto transfers. The platform’s standout features include EVM-compatible on-device signing, multi-
stablecoin wallets, partner-scoped APIs (for “employers” to onboard linked users), and issuance of virtual/
physical spend cards on each wallet【32†L67-L75】【45†L95-L104】. BMONI provides comprehensive REST
APIs and Flutter/React-Native SDKs for integration.
This reconnaissance document inventories BMONI’s capabilities: user flows, API surface, SDK details, wallet/
key architecture, country-rail mapping (with Nigeria focus), sandbox/test data, webhooks, AI/
documentation tooling, plus ideation of product opportunities and hackathon considerations. Each major
component is mapped with exact endpoints, parameters, and life-cycle diagrams. The API Catalogue
details every endpoint by domain (Users, SmartWallets, KYC, Onboarding, Fund, Transfers, SWAPS, Rails,
Cards, Webhooks, etc.), with method, path, auth, params and sample responses. Diagrams illustrate core
flows: (1) User onboarding → smart-wallet provisioning → USD-virtual-account deposit → pay another
user, (2) Employer linking flow (invite → employee KYC → account link), (3) Card issuance and
activation. We compare the Flutter vs React Native SDKs: both generate a secure on-device Ethereum
wallet (Android Keystore / iOS Secure Enclave) and identical API methods (initWallet, signMessage, etc.)
【32†L67-L75】【30†L59-L68】. We highlight security (private keys always device-bound, PIN-protected), 
webhooks (event types like employee.deposit.completed , HMAC signature verification), and sandbox
tools (test personas and BVNs【26†L193-L201】, test token credits). A country/currency matrix shows
supported fiat rails per region. Lastly, we identify high-value hackathon ideas (multi-currency remittance,
payroll cards, crypto integration), assess technical risks (e.g. unprovisioned KYC, 3rd-party dependencies,
on-device signing in web), and recommend technology stacks: mobile-first (Flutter) to leverage BMONI’s
UI and SDK libraries, or React Native as a viable alternative; web is possible but requires custom signing
work. 
Citations are drawn only from official sources (BMONI docs and site). Inferences and design proposals are
clearly marked and justified. This report is exhaustive, aiming to leave no question unanswered for a
product engineer exploring BMONI Embedded.

1. BMONI Product Overview
BMONI (by BKEY Inc.) is a cross-border digital financial platform targeting globally-mobile individuals and
businesses【59†L185-L194】. Unlike a bank, BMONI leverages licensed partners to provide onramps/
offramps in multiple currencies. Key use-cases include expats sending money home, remote workers and
freelancers managing multiple currencies, global families (parents abroad), and small businesses
paying global suppliers or employees. Users download the BMONI app (iOS/Android), sign up with phone +
KYC (face scan, ID, proof of address, etc. – Nigeria users must supply BVN【59†L219-L224】). Once
onboarded, each user can create multiple smart-wallets, each in a different supported currency (USD,
NGN, EUR, CAD, MXN, etc.)【14†L81-L90】. Each wallet holds a stablecoin pegged to that currency (e.g.
“USDB” for USD, “CNGN” for NGN【14†L81-L90】【59†L272-L279】) and is self-custodied on the user’s
device via an Ethereum key pair . 
Primary capabilities and flows:
Multi-currency wallets: Users can top-up (on-ramp) wallets in local currency via bank transfer (e.g.
USD → USDB, NGN → CNGN) or crypto deposit, then spend or withdraw via various rails. 
Currency conversion (swap): Users can convert between their BMONI balances (e.g. USDB↔CNGN)
at real-time rates via an API endpoint. 
Stablecoin-backed balances: All major currency balances are underpinned by regulated stablecoins
backed 100% by fiat reserves【59†L272-L279】. For example, USDB is fully collateralized by USD in
US banks【59†L272-L279】. 
KYC & compliance: BMONI handles global KYC. For example, Nigerian users present BVN/NIN;
Europeans use Monerium IDs; Mexicans use Etherfuse【14†L81-L90】【40†L95-L104】. Once KYC is
approved, all multi-currency functionality is enabled. 
Bank rails: Virtual accounts are provisioned for USD (ABA routing), NGN (NUBAN), and IBAN (EUR/
CAD)【14†L81-L90】【39†L131-L139】. Users are credited stablecoins upon deposit. Offramp rails
include payouts to bank accounts in supported countries (SEPA, NGN payouts, MXN CLABE, etc.). 
Global cards: BMONI issues Mastercard-branded debit cards (virtual/physical) in NGN or USD,
funded by a smart wallet【45†L75-L84】. Users can activate, freeze, set limits, and view transactions
via the API. 
Partnership/embedded model: BMONI can be embedded in other apps or platforms. It provides a
partner API for e.g. employers to invite and manage employees’ BMONI wallets without building
their own app【24†L1-L4】【52†L441-L449】. 
Security: Each wallet’s private key is generated/stored in device secure hardware (Android Keystore /
iOS Secure Enclave) and never leaves the device【32†L67-L75】【30†L59-L68】. All sensitive
operations (transactions, card issuance, payout approvals) require an on-device signature from the
wallet’s key (via the BmoniEmbeddedSdk). Additionally, BMONI uses patented facial recognition for
login/transaction authorization【59†L191-L194】. 
In sum, BMONI is a cross-border e-wallet platform combining fiat rails, stablecoins, and card services. It
abstracts away crypto complexity: users think in local currency, while BMONI performs any needed swaps
between USD stablecoins and local currency rails【40†L197-L200】. This positions BMONI between a digital
bank and a crypto-stablecoin app, offering globally interconnected money movement.

2. Architecture
BMONI’s backend is a proxy linking clients (apps) to multiple underlying rails and services. Its architecture
can be summarized as follows:
Self-custodied smart-wallet contract: When a user provisions a wallet, BMONI deploys (or
allocates) a wallet contract or EVM keypair unique to the user on Ethereum-like chains. The user’s
device holds the owner key (via SDK). The backend tracks each wallet’s address, currency, chain, and
status. 
Stablecoins: For each supported currency, there is a corresponding ERC-20 stablecoin (e.g. USDB,
CNGN, EURe, CADC, MEXe). These stablecoins are minted/burned on deposits/withdrawals. Actual
fiat is held in partner bank accounts (e.g. USD in US banks, NGN in Nigerian banks【59†L272-
L279】). 
Fiat rails via integrations: BMONI integrates with bank APIs and regional rails: e.g. an API call to a
Nigerian bank to create NUBAN, or to Etherfuse for Mexico CLABE, or to Monerium for EUR IBAN. It
also uses payment providers (e.g. Pago46 for cash pay-points). The ‘prepare-sign-complete’ pattern
is common: e.g. a USD wire is prepared (account given) then signed by user , then processed. 
Backend proxy (Node.js, etc): The partner calls BMONI API (x-api-key auth). BMONI’s server
implements endpoints, orchestrates multi-step flows, calls fintech partners and its own smart-
contract proxies, and returns status or signature requests. 
Webhooks and event service: BMONI uses webhooks to notify partners of asynchronous events
(deposits, onboarding completion, card issuance, etc). It signs payloads with HMAC using a partner-
specific secret【48†L159-L169】. 
SDK/clients: The BMONI frontend (or integrators) use the mobile SDK (Flutter or React Native) to
handle key-generation and on-device signing【32†L67-L75】【30†L59-L68】. The UI uses Bkey UIKit
components (Flutter package) for consistent look. 
Sandbox environment: A shared BMONI sandbox (embedded.bmoni.com) mimics the API for
testing. Sample personas (with pre-known BVN/NIN) are provided for identity checks【26†L193-
L201】. Test bank accounts are provisioned with synthetic funds via request form【27†L0-L5】.

Key architectural notes: Private keys never leave device (secure enclave)【32†L67-L75】. BMONI is
architected to treat each wallet as a distinct on-chain entity. All important actions (minting stable tokens,
payouts, creating cards) require user signature from the corresponding smart-wallet key. This ensures
security but means integrations must incorporate signing flows for transfers, redemptions, and card
issuance.

4. SDK Deep Dive (Flutter vs React Native)
BMONI provides client SDKs for Flutter and React Native (both named bmoni_embedded_sdk  on
pub.dev/npm) to manage on-device wallets. The SDKs are equivalent in capability and design, differing only
in language and platform setup【30†L59-L68】【32†L67-L75】. 
Purpose: Both SDKs generate and store a secp256k1 keypair on the user’s device and perform
cryptographic signing. Keys are protected by a user-chosen PIN (configurable length) and the
device’s hardware root of trust (Android Keystore or iOS Secure Enclave)【32†L67-L75】【30†L59-

6. Wallet and Signing Architecture
Each BMONI smart wallet is a separate EVM account whose private key is only on the device. Under the
hood:
The BMONI server registers each wallet with a userOwnerAddress  (the EOA address from 
initWallet() ).
Whenever the server needs the user’s signature (in a signatureRequest ), it includes the message
to sign (ABI-encoded call data or a human-friendly string). The client uses signMessage()
(EIP-191) or signTransactionHash()  to sign it【32†L89-L94】.
The signed message is sent back to BMONI via an API ( /wallets/submit-signature  or similar)
to finalize the action. The server then relays it to the blockchain or partner system.
Local vs Backend: Account nonces, addresses and balances are tracked server-side in a database (for
efficiency), but actual token transfers occur on-chain. The server never has the user’s private key
(only the device does). Secrets (PIN, seed) are never in the cloud. The user’s phone must be online to
sign critical operations (though non-sensitive calls can be done server-to-server). 
Recovery: If a user loses their device, BMONI provides account retrieval via phone + face scan (the
wallet seed is tied to KYC identity, not stored by BMONI)【59†L193-L194】.

7. KYC and Identity
BMONI’s flows are gated by KYC at the user level and (for partners) at the employee level. Relevant points:
Global KYC: The /kyc/readiness  and /kyc/activate  endpoints capture standard info.
Nigerian users provide BVN / NIN 【26†L193-L201】; others use respective IDs. All KYC fields
(employment status, income source, etc.) must satisfy the validator or return error messages
【29†L143-L152】. 
One-time submission: KYC is submitted once; all on-ramps reuse it. For example, after Nigeria KYC,
user can do NGN and USD rails without re-verifying (though USD rail has additional field checks
【39†L97-L104】). 
Automated lookups: Sandbox supports BVN/NIN lookups to prefill name【26†L193-L201】. In prod,
the KYC endpoints integrate with verification partners (onboarding flows show Monerium, Etherfuse,
PayTrie, etc). 
Errors: Common validation errors (BVN length, etc) are documented【29†L149-L157】. Notably,
deleting an account requires zero balance (Error E101). 
NRW (Rest of World): For non-specified regions, a generic KYC flow exists (e.g. if not in NGN/EUR/
MXN/CAD locales). 
In short, KYC is thorough: collects name, DOB, address, ID scans, and country-specific IDs. The APIs expose
both readiness ( GET /kyc/readiness ) and specific onboarding ( /onboarding/start-xxx ) steps.
Webhooks onboarding.completed  and kyc.action_required  notify of progress【52†L423-L432】,
eliminating long polling.

9. Nigeria Rails
Nigeria-specific rails combine NGN and USD handling:
NGN Onramp: As soon as /onboarding/start-nigeria  is called (and KYC active), BMONI auto-
provisions a NUBAN virtual account for CNGN . To attach it: POST /smart-wallets/{w}/onramp/
vba/nigeria 【40†L95-L104】. Retrieve the NUBAN via GET /bank-accounts/deposit-
accounts/NGN  (single-element array). All NGN transfers to that NUBAN automatically credit the
user’s CNGN balance. Deleting the onramp ( DELETE ) stops new deposits. 
NGN Offramp: Three steps as per docs【40†L128-L138】: (1) GET /bank-accounts/nigerian-
banks  to list banks+CBN codes. (2) POST /bank-accounts/verify-nigerian-account  with
NUBAN and bank code to fetch the registered account holder name【40†L140-L149】. (3) POST /
bank-accounts/withdrawal-accounts/nigeria  to register that account (or reuse existing),
providing NUBAN, code, bank name, holder . (4) Finally, POST /smart-wallets/{w}/offramp/
nigeria  with bankAccountId  and fromAmount 【40†L184-L193】. This initiates a withdrawal. It
returns a proposalId for finalization (signature step). The withdrawal amount is specified as a
decimal string (e.g. "100.00" )【40†L184-L193】, which is noteworthy because other APIs use
minor units (e.g. bank payout uses "100000000"  for 100 NGN【38†L226-L234】). 
USD Onramp (for Nigerian users): After completing NGN, a Nigerian user can also set up a USD VA.
They must call /onboarding/start-usa  with their smartWalletId【39†L115-L124】. BMONI then
creates a US bank account (ACH) for the user to receive USD → credits USDB when money arrives.
Polling GET /vba/usd  returns account# and routing once status:active 【39†L131-L140】.
The USD rail requires extra KYC fields (employment, source of funds) via GET /kyc/usd-
readiness 【39†L97-L104】. There is no USD off-ramp (no direct USD transfer out) – to withdraw
value, a user would convert USDB to NGN or to another currency and use another rail. 
Error conditions: Trying to withdraw more than the wallet’s balance triggers 400 . If KYC is
incomplete, /offramp/nigeria  will fail (one must wait for 
employee.onboarding.completed ). If funds are pending, the webhooks 
employee.withdrawal.processing/completed/failed  will indicate when money leaves or
fails【52†L409-L417】.

16. Errors and Edge Cases
BMONI uses standard HTTP status codes with JSON bodies containing statusCode , message , and 
error 【29†L90-L98】. Key patterns:
Validation (400): Field errors come as an array of messages【29†L114-L123】. For example, “BVN
must be exactly 11 digits”. On 400, fix inputs and retry. 
Auth (401/403): Missing or wrong x-api-key  yields 401. 403 Forbidden  if you try to access a 
bmoniUserId  belonging to another partner【29†L179-L187】. 
Not Found (404): If you use a non-existent userId, or request data not yet provisioned (e.g. polling a
VA too early), you get 404 with “requested item could not be found”【29†L192-L200】. The docs note:
“A 404 does not always mean missing”【29†L196-L204】—it can mean “not ready yet” (e.g. wallet not
yet deployed). Treat it as retry case unless the item truly doesn’t exist. 
Conflict (409): Conflicts (e.g. creating a user with existing phone/email) yield 409. Also see cards: 
409  on /sign-payload  means payload not ready yet【45†L143-L152】. 
422 and others: Rare; unspecified here. 
Error message shape: The JSON might have "message"  as a list (validation) or single string. Do
not parse semantically (they warn it can change wording)【29†L101-L109】. 
Special Cases: Deleting user requires empty wallets (E101 error)【27†L0-L5】. If an asynchronous
step is still in progress, many endpoints will either return 404/not found or a status=“pending”/
“provisioning” which you should poll on (e.g. VA provisioning). 
Always handle errors gracefully: log them, surfacing user-friendly messages, and retry appropriately for
transient states. The integrated docs emphasize that many workflows (onboarding, bank linking) rely on
webhooks instead of polling, to avoid error-prone retry loops.
17. Security Considerations
Authentication: Only API key is used; no OAuth or JWT. Protect the x-api-key  like a password.
Separate keys for sandbox vs prod. 
Data protection: Do not log or expose sensitive fields. For example, never log wallet secrets or full
card data. When using /cards/sensitive-data , treat output as cardholder data (PCI rules)
【47†L233-L242】 – don’t cache or log it. 
HTTPS only: All endpoints are SSL. Use pinned certificates as needed. 
Signing: Perform all signing operations on-device only. The SDKs ensure keys are hardware-backed.
Do not attempt to move keys to server . 
Webhooks: Verify each delivery via HMAC【48†L169-L177】. Reject any webhook failing signature
check. Also validate that X-Webhook-Id  (or body id) hasn’t been processed to avoid replay. 
Rate limits: The docs do not specify rate limits, but treat the API as a paid cloud service. Poll
judiciously. Webhooks exist to avoid polling. 
Partner isolation: Each partner’s bmoniUserIds  are segregated. Attempting to mix up scopes
returns 403【29†L179-L187】. Store your partnerId and use it in webhook config; do not omit it (or
you’ll get legacy global events). 
Overall, BMONI’s security model relies on strong cryptography (EIP-712 signatures) and KYC. For our
integration, ensure we follow best practices (secure storage for webhook secrets, limit access to API keys,
etc.).

21. Hackathon Constraints & Risks
Time & Complexity: Building a full fintech solution is ambitious. Focus on a minimal viable flow (e.g. one
currency onramp and one use-case). Leverage existing UI kits and widgets (Flutter) to save time. 
Regulatory: BMONI handles KYC, so compliance burden is lower . However , understand sandbox vs
production differences. In production, any crypto involvement requires caution (stablecoin custody rules). 
Technical: On-device signing means web-only demos are tricky. If building a web frontend, you’ll need a
substitute for the signing SDK (e.g. MetaMask or web crypto) – not straightforward. Better use mobile. Also
note iOS simulator cannot run key signing (no Secure Enclave) – test on devices or Android emulator . 
Dependencies: BMONI’s rails rely on third parties (banks, payment providers). In sandbox these are
stubbed, but in real use some rails might fail or be slow. For hackathon, use webhooks to avoid polling
waits. 
Sandbox vs Prod: Some sandbox behaviors differ (e.g. static test data). Confirm which is allowed: issuing
too many cards or orders in sandbox might hit limits. Also, ensure your x-api-key  is for sandbox, not
accidentally production. 
Avoiding Clones: Don’t simply copy features of established apps (like Venmo splits, Coinbase wallet).
Instead emphasize BMONI’s unique data (multi-currency, on-chain). For example, don’t just recreate a
standard pay app; add something novel like auto-conversion or stablecoin rewards. 
Team Skill: Ensure team members know Flutter or RN and possibly some crypto/web3 basics. Using the
SDK means you need to handle asynchronous flows (signing) properly. Familiarize with the example flows
before hackathon day.
22. Recommended Technology Stacks
Flutter: The top recommendation. Flutter’s bkey_uikit  + bmoni_embedded_wallets_cards  provide
ready UI widgets (wallet cards, typography, forms)【35†L74-L80】【36†L59-L68】. Combined with the 
bmoni_embedded_sdk , one can prototype a wallet app rapidly on Android/iOS. Flutter’s hot reload and
cross-platform nature accelerate dev. (Downside: must manage native build environment; large binary size.)
React Native: Also supported, with an equivalent bmoni_embedded_sdk  for RN【30†L59-L68】. Use if

RN requires RN 0.76 (new arch) and manual Maven config【34†L119-L128】. There is no RN UI kit from Bkey
yet, so you’d build UI mostly from scratch or use other libraries.

wallet integration (e.g. MetaMask) to sign transactions, and there is no direct support for generating wallet
keys in browser via BMONI. This means skipping the SDK: you’d have to have your own private key
management (complex) or send transactions to BMONI (unlikely). Therefore, a purely web approach is high

PIN gating: Client can enforce a 4–6 digit PIN for every sign operation【33†L134-L143】【30†L85-

Flutter widgets (Flutter only): The bmoni_embedded_wallets_cards  package provides high-

All signatures EIP-2 compliant: The outputs are low-s normalized, ready for ecrecover  checks on

Unified API: Both Flutter and RN share the same method names (e.g. initWallet() ,

porting is trivial. 
These capabilities mean a mobile app developer can secure funds just with BMONI’s libraries – a rare
turnkey solution. Typical fintech APIs don’t handle keys at all (they rely on OAuth), so BMONI’s edge is
building a true on-device crypto wallet with minimal effort.
E. Unique Possibilities
BMONI makes two things possible that most fintech APIs do not: easily fusing on-chain crypto with fiat
rails, and custom wallet issuance. Specifically:
Real stablecoin balances: Users literally own stablecoins under their control. This enables
integrations like sending stablecoins internationally (trust-minimized) rather than via intermediary
accounts. 
Seamless forex: The system auto-swaps stable currencies during transfers, enabling instant multi-
currency payments without human FX steps. 
Programmable wallets: Because each wallet is an Ethereum account, you could integrate it with
other smart contracts (e.g. DeFi, escrow) outside BMONI, a possibility standard APIs lack. 
Embedded wallet-as-a-service: The partner invite model ( employee.linked  flow) effectively lets
companies onboard employees into a custodial wallet system without building it themselves – an
uncommon offer . 
Multi-rail in one API: Developers get USD ACH, Naira rails, SEPA, Latin cash, crypto all from one
backend. 
In a nutshell, BMONI is more than a payments API; it’s a blockchain-enabled global banking stack. It
merges elements of PayPal, Coinbase Wallet, and issuance systems into one.

F. Best Hackathon Opportunities
Given BMONI’s strengths, some high-impact hackathon products include:
Cross-border Payment Aggregator: An app that finds the best route for sending money abroad
(e.g. "Get $→Deliver NGN"). Behind the scenes, use BMONI’s exchange and rails to offer low-fee
remittances. 
Multi-Currency Wallet App: A budgeting or travel wallet that auto-manages holdings in USD, EUR,
NGN, MXN, etc. with real-time conversion via BMONI. 
Payroll/Expense Card Service: A system where employers fund wallets and issue cards to
employees in multiple countries – all handled via BMONI’s API (no HR onboarding code needed
beyond invite). 
Stablecoin Savings Program: Leverage on-chain deposits of USDC/DAI, then lock into BMONI
(USDB) to earn fixed yields or rewards (maybe combine with an AI advisor). 
AI Financial Coach: Combine BMONI’s account data (via APIs/webhooks) with a chatbot that advises
on spending, budgeting or forex timing. 
These ideas exploit BMONI’s unique rails and on-device crypto. For instance, typical P2P payment apps don’t
do stablecoin swaps or auto-rail selection. BMONI’s wallet-card combo is ideal for a next-gen global banking
app. Emphasize scenarios where money crosses borders or currencies – that’s where BMONI shines.
G. Impressive Technical Possibilities
End-to-end on-chain payment: Show a user’s USD VA deposit automatically minting USDB on EVM
and crediting their on-chain balance, all in one transaction flow. 
Live swap rate execution: A real-time quote API call triggering an atomic swap (via EVM) on the
stablecoin contract. 
Programmable card spends: Automatically adjusting card limits or locking cards via API based on
user-defined triggers or AI analysis. 
Complex multi-hop rails: E.g. user deposits BTC to BMONI (if allowed), BMONI sells to USDB, then
off-ramps to NGN in one seamless flow (combining crypto deposit, internal exchange, and NGN
payout). 
Blockchain audits: Because every step has a signature, you could verify history on-chain –
something conventional fintech doesn’t allow. 
The most impressive demo might be cross-border mobile pay: User A in USA deposits USD, converts to
CNGN, and instantly is able to pay User B’s card or account in Nigeria via API, with all steps signed and
verifiable. It showcases the breadth of rails in a single user story.
H. High-Risk/Complex Capabilities
Direct crypto custody: Users handling stablecoins means they could send them outside the
platform. There’s risk in crypto integration (if BMONI allowed minting from arbitrary crypto, etc). For
hackathon, avoid any true custodial crypto trading. 
Regulatory KYC gaps: If a country-specific KYC call is missed, user might get stuck. E.g. forgetting to
collect BVN for Nigeria can block NGN rails. Automated flows must cover all KYC steps or handle 
onboarding.failed  events.

Concurrency in swaps: Exchanging large amounts may cause slippage or rate issues. The APIs
assume a single-threaded use; rapid calls or race conditions could mis-handle funds. 
Web integration risk: Without native SDK, anyone trying to do on-device signing via browser might
expose keys. This is very risky; we mark web wallet flows as highest technical risk. 
Dependency downtime: If a Rails partner (say, Nigerian bank API) is down, API calls for VA creation
might hang or fail. We should handle timeouts and errors for production readiness. 
Uncapped operations: Some APIs (like card issuance or payouts) might have caps or require extra
approvals beyond docs. Triggering them in sandbox vs real might differ . 
In summary, rely on the provided flows and avoid inventing sideways paths (like custom crypto funds). The
system itself handles security; the hackathon should avoid tampering with core signing. Logging &
monitoring are also important for catching failures (e.g. webhook failures).
I. Recommended Tech Stack
Frontend: Flutter (Dart) as first choice – it directly uses BMONI’s design system and wallet card
components【35†L74-L82】【36†L59-L68】. Alternatively, React Native if the team is stronger in JS.
Both support BMONI’s wallet SDK【32†L79-L88】【30†L59-L68】. 
Backend: Node.js/Express or Next.js API routes to handle server logic (storing user IDs, calling

Database: Minimal, but something like SQLite or Mongo to store bmoniUserId , wallet IDs, maybe

Deployment: If public expo needed for webhooks, use a cloud function or service like Render , Vercel,
